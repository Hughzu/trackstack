# Architecture Blueprint: Multi-Domain Tracking Frontend Migration

## 1. Context & Philosophy
* **Profile:** Architect / DevOps / Platform Engineer.
* **Goal:** A tracking application covering multiple domains (Calories, Expenses, Heat/Pellets, SRL).
* **Principles:** No-nonsense, maximum performance, near €0 infrastructure cost, strict typing, "LLM-Friendly".
* **Anti-patterns:** No React, no over-engineering JS, no "unemployed tooling".

## 2. Technical Stack
* **Frontend:** Solid.js (SPA) + Vite + PWA.
* **Language:** TypeScript (strict mode).
* **State Management:** Native Solid signals (`createSignal`, `createMemo`).
* **Design System & Styling:** TailwindCSS centralized exclusively in generic UI components (`src/components/ui/`). We use dynamic CSS Custom Properties (e.g., `--color-accent`) injected at runtime via environment variables (`VITE_DEPLOY_TARGET`) to distinctively brand the app based on its deployment target (VPS, Serverless, K8s).
* **Routing:** `@solidjs/router` (Explicit lazy-loading configuration in `src/routes.tsx`).
* **API Client:** `openapi-fetch` (strictly typed client generated from the Go backend's `openapi.yaml` to guarantee a Single Source of Truth).
* **Testing:** Playwright for E2E tests, adapted from the previous SSR/MPA behavior to asynchronous SPA state and API response waiting.

## 3. Migration Strategy (`apps/web-next`)
To ensure a secure transition, we will **not** immediately delete the current Astro implementation.
* The new Solid.js SPA will be bootstrapped in `apps/web-next`.
* We will use `apps/web` as a business logic and structural reference during the rewrite.
* Once feature parity and Playwright tests pass, we will swap the folders and drop Astro.

## 4. Code Architecture (Domains)
Domain-driven structure designed to support a potential future split into micro-frontends. The implementation will be phased: Auth -> Dashboard -> Calories -> Expenses -> Heat.

```text
src/
  core/            # Auth logic, global api client instance, generated openapi schema
  styles/          # global.css (Tailwind init + CSS variables based on env)
  components/ui/   # Design System (Reusable atomic components containing Tailwind classes)
  features/        # Isolation by business domain
    auth/
    dashboard/
    calories/
      components/  # Domain-specific components
      stores/      # Domain-specific signals
      api/         # OpenAPI fetch wrappers for this specific domain
      index.tsx    # Feature entry page
    expenses/
    heat/
  routes.tsx       # Centralized routing definition (Lazy Loading)
```

## 5. Infrastructure Strategy (AWS)
* **Hosting:** S3 Bucket (Static Website Hosting).
* **Distribution:** CloudFront with optimized Cache.
* **SPA Routing:** CloudFront Error Path 404 -> `/index.html` (HTTP 200).
* **Backend:** Go (Hexagonal Architecture) deployed on AWS Lambda.
* **Interface Contract:** OpenAPI/Swagger acting as the strict "Single Source of Truth".

## 6. Prompt Guidelines for LLMs 
* **Code Style:** Prefer pure functions and Solid.js declarative approaches. Never use Virtual DOM patterns (no `useEffect`, use `createEffect` sparingly).
* **Signals:** Always default to signals for fine-grained reactivity.
* **Design:** STRICT ZERO-TAILWIND POLICY IN FEATURES. Tailwind utility classes are strictly forbidden inside `src/features/`. They belong exclusively in `src/components/ui/`. If a feature component needs layout (e.g., flex, gap, margin), you must extract that layout into a reusable UI component. Do not hack inline layout classes in domain components.
* **Types:** Always use the types generated by `openapi-typescript`. Never manually redefine interfaces originating from the backend.
* **Testing:** When writing Playwright tests, do not rely on full page reloads (`waitForNavigation`). Use API-based assertions (`waitForResponse` or locator visibility waits).
* **Route Files:** Treat `src/features/**/index.tsx`, `new.tsx`, `settings.tsx`, and other route-entry files as thin controllers only. They may fetch data, own route-level mutation state, and compose extracted subcomponents. They must not become dumping grounds for page-local cards, dialogs, or long JSX slabs.
* **Feature Components:** When a route needs multiple panels, cards, forms, or sections, extract them into `src/features/<domain>/components/` immediately instead of nesting helper components inside the route file.
* **Layering:** Feature display/mapping helpers must not import types from `src/components/ui/`. UI primitives should consume feature-local view models, not dictate the shape of domain mapping code.
* **Shared Patterns:** If the same interaction pattern appears across routes or domains (confirmation sheets, destructive action flows, skeleton sections, repeated form action layouts), promote it into `src/components/ui/` instead of duplicating bespoke versions inside features.

## 7. Loading Experience (Skeletons)
To maintain a premium feel and zero Cumulative Layout Shift (CLS):
*   **The Ghost Twin Principle:** Skeletons must be a 1:1 structural "ghost" of the final component. 
*   **Physics Parity:** Always match the exact padding (`p-5`), border-radius (`rounded-2xl`), and margins (`mb-4`) of the `Panel` component.
*   **Typography Matching:** Use specific heights for skeleton bars that match the line-height (leading) of the text they replace (e.g., `h-3` for `text-xs`, `h-4` for `text-sm/base`).
*   **App Shell Persistence:** Never hide the `AppShell` (header/nav) during loading. Only skeletonize the `main` content area.
*   **Animation:** Use `animate-pulse` for placeholders. Use `animate-in fade-in` for the final data arrival to smooth the transition.

## 8. Collaborative UI Design & Mocking Process
When iterating on feature mocks and UI design, we enforce a strict, challenge-driven workflow:
*   **Semantic Strictness:** All UI atoms (`Stat`, `ProgressBar`, `Skeleton`) strictly communicate through UI design-system enums (e.g., `variant="lg"`, `color="danger"`, `titleVariant="md"`). We NEVER pass raw margin, padding, or width/height Tailwind utility classes as component props (down to the skeleton text block level). The logic mapping a semantic variant to a structural width/height is encapsulated entirely inside `src/components/ui/`.
*   **Zero-Redundancy Mocks:** We actively eliminate redundant information. If detailed breakdown text natively exists, summary visualizers (like progress bar legend labels) are stripped away. This allows elements to stack tightly and naturally without relying on arbitrary layout spacing hacks.
*   **Contextual Track Visibility:** Empty states and progress tracks must communicate scale intuitively. We explicitly style empty tracks in low-contrast thematic scales (e.g., `bg-border/50`) so partial completions are immediately recognizable against the card backgrounds.
*   **Challenge Assumptions (No Boilerplate Padding):** We actively challenge layout spacing defaults. We strip out boilerplate mobile padding classes (e.g. `pb-24`) that create dead space and artificial scrollbars when desktop interfaces fit neatly in the viewport.

---

### Why this approach? (Note for LLMs)
Dropping **Astro** for a pure **Solid.js SPA** means saying goodbye to SSR, but it perfectly aligns with the goal of serving a standalone static shell from S3 (cost efficiency) interacting with a Go API. By keeping **Tailwind** but strictly containing it within the UI components library, we retain rapid development without cluttering the business domain files. The dynamic CSS variables natively solve the multi-environment theme requirements (Serverless vs K8s vs VPS) without duplicating CSS rules.
